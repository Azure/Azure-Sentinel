| 3.2.0       | 18-09-2026                     | • **Two-way status sync.** Alert status is now mirrored between Argos and Microsoft Sentinel in both directions, with the newest change winning.<br>• **Data connector** polls on `update_date` instead of `created_date`, so every change to an Argos alert adds a row to `argsentdc_CL`, and requests 100 alerts per page instead of the API default of 10, which had silently capped ingestion at 10 alerts per polling window.<br>• **New analytic rule, Check Point Exposure Management - Argos alerts to incidents**, replaces the **Check_Point_EM_Importer** playbook. The Importer wrote to the built-in `SecurityAlert` table through the Logs Ingestion API, which does not support that table, so it could never ingest. The rule creates one incident, with an attached alert and the `ref_id` Custom Detail, the first time an alert appears as `open` or `acknowledged`; later changes to the alert never create another incident.<br>• **New playbook, Check_Point_EM_InboundStatusSync**, applies Argos status changes to the matching incident every 5 minutes, mapping closure reasons to Microsoft Sentinel classifications.<br>• **Check_Point_EM_Exporter** reads each Argos alert before writing and skips it when Argos already has the target state, which prevents sync loops and replaces the `argos-importer-synced` tag check. An Argos closure reason counts as already in sync when it maps to the incident's classification, so reasons such as `asset_should_not_be_monitored` are not overwritten with `no_longer_a_threat`. Each `ref_id` is synced once per run instead of once per attached alert. It is now wired by the **Check_Point_EM_AutomationRules** template, which shipped in the repository but was never part of the package, and which now fires on every status change instead of only on close.<br>• **Status mapping fixes** in the Exporter and **Check_Point_EM_ManualStatusUpdate**: `Active` maps to `acknowledged` (was `open`); `FalsePositive`/`InaccurateData` maps to `irrelevant_alert_subtype`; `Undetermined` sends `other` with the classification comment (trimmed to 255 characters, `undetermined` when empty) as the closure reason description.<br>• **Status update request fixed**: the playbooks called `PUT /api/v1/alerts/{ref_id}`, which does not exist; they now call `PUT /alert/api/v1/alerts/status` with the documented `alert_ref_ids` and `data` envelope, and omit `closure_reason` when not closing.<br>• **`ref_id` extraction fixed** in the Exporter, ManualStatusUpdate, FetchAttachments and PhishingTakedown playbooks. Microsoft Sentinel delivers `Custom Details` as a JSON string of arrays, so the previous expression failed with "Property selection is not supported on values of type 'String'".<br>• **`API_Base_URL` takes the tenant URL** (for example `https://your_tenant.cyberint.io`), the same value as the data connector, in the Exporter, ManualStatusUpdate, FetchAttachments and PhishingTakedown playbooks. The service path is added automatically; values ending in `/alert` keep working. PhishingTakedown now submits to `/takedown/api/v1/submit`.<br>• **Workbook** summary tiles count each alert once by its latest status.<br>• **Upgrading from 3.1.x:** reconnect the data connector so it polls on `update_date`; create a rule from the Argos alerts to incidents template; recreate the Exporter, ManualStatusUpdate and AutomationRules playbooks from their updated templates and create InboundStatusSync, then grant each the **Microsoft Sentinel Responder** role; disable or delete any existing **Check_Point_EM_Importer** Logic App, its API connections and its data collection endpoint. `argsentdc_CL` now holds one row per alert change, so custom queries should take the latest row per `ref_id`. |
| 3.1.4       | 08-09-2026                     | Fixed **Check_Point_EM_Importer** playbook creation failing with `InvalidTemplate: Unable to parse language expression '': expected token 'Identifier' and actual 'EndOfData'`. The empty `Entities` JSON array literal in the SecurityAlert ingestion body was interpreted by ARM as an empty template expression; it is now emitted via `string(createArray())` in both the solution package and the standalone playbook template. |

Optional filters now default to empty and are omitted from the request. |
